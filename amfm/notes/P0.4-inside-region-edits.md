# What was asked

PM checkpoint, item 3, called the critical remaining Product check:

> A warning can be an acceptable *explicit invalidation/conflict state* only if
> the Owner can understand which surface is stale and can resolve/remove/recompute
> it without hiding a deletion under apparently intact geometry. Demonstrate this
> with **one inside-region deletion and one recolor** on the real ship, before/after
> visible and documented. Do not label unchanged geometry with edited occupancy a
> proven 'no ghost shell' solely because its mesh hash is unchanged. If the surface
> remains visibly intact over a deleted cell, this must be reported as a known
> limitation or corrected within the existing P0 scope.

That criticism was correct. The previous round's "no ghost shell" claim rested on
the mesh hash being unchanged, which proves only that the surface did not
rebuild — not that the Owner can see or resolve what happened. Item 6 also asked
for a fresh clean-build and targeted memory-check record after the out-of-bounds
fixes, which is at the bottom of this note.

# The honest answer first

**Yes: the surface stays visibly intact over a deleted cell.** A generated surface
is built from the region box, so deleting one cell inside that region does not
change it. The deletion is real and it is hidden under geometry that looks fine.
That is a genuine limitation of the region-derived model, and it is now recorded
as such in the self test rather than being dressed up as a proof:

```
[PASS] a cell inside the region really is deleted -- deleted [-60 -5 -5], 715 -> 714 cells
[PASS] KNOWN LIMITATION: the surface still hides it -- mesh 3845648702 -> 3845648702
```

What was missing was the second half of the PM's condition — that the Owner can
tell *which* surface is stale and resolve it. That is now implemented, so the
state is explicit rather than silent.

# What was corrected

**Staleness is a property of the shape, not of an open dialog.** The modifier
carries `applied_hash` (the hash of its own layer's cells inside the region at
Apply time) and a derived `stale` flag. `applied_hash` is now **persisted** in the
`LAYR` record, which grew to 11 ints; 7-, 8- and 10-int records still read back,
so older documents still open. Without persisting it, a stale shape would look
clean again after a save and reopen — the worst case, and the one the PM was
pointing at.

**The stale surface is visible in the viewport.** A stale shape renders in a
magenta warning tint — neither the hull colour nor the warm live-preview tint — so
"which surface is stale" is answerable at a glance with no panel open. The flag
refreshes when the shape layer is selected (including one that was already stale
before the file was saved) and a few times a second while a shape session is open.

**The strip states the situation and offers both resolutions.**

> STALE: cells inside this region changed after the shape was applied. The surface
> is built from the region, so it did NOT change to match them. Resolve it one way
> or the other:
> **Accept edits**  |  **Restore cells**

* *Accept edits* keeps the surface and re-baselines against the cells as they now
  are — the flag clears because the Owner has decided.
* *Restore cells* drops the modifier. The source cells were never deleted, they
  live on that same layer, so the layer immediately renders as ordinary voxels
  again: the original geometry returns and nothing is thrown away. This is also
  the general escape hatch that was missing before — after a save/reopen there was
  no undo history, and deleting the shape layer would have deleted its cells.

# The demonstration on the real ship

`GOXEL_EDIT_DEMO=1` → `evidence/edits/`. One slope on the bow block of `vox1.vox`
(region `[-64 -24 -20]..[-46 23 -1]`, 10,092 cells), then one deletion and one
recolour inside that region, each photographed before and after:

| frame | what happened | what it shows |
|---|---|---|
| `edit0.png` | slope applied | the generated wedge, normal colour |
| `edit1.png` | cell `[-48 -16 -20]` deleted inside the region (10,092 → 10,091) | **same silhouette**, now magenta: the deletion is hidden, the staleness is not |
| `edit2.png` | cell `[-47 -16 -20]` recoloured inside the region | still the same silhouette, still magenta |
| `edit3.png` | *Restore cells* | the source voxels return as stepped geometry; the recoloured cell is now **visible as a green voxel**, and the deleted cell's absence is real |

`edit3` is the frame that makes the whole thing honest: the recolour had been
happening the entire time underneath the surface, and once the surface is resolved
away the cell edits are visible and the geometry is intact minus the one cell the
Owner deleted. Cell totals at the end: `138,291 + 10,091 = 148,382` = 148,383 − 1
deleted ✓.

# A real geometry defect this check exposed

Making the rendered footprint traceable to its source region caught a genuine
bug in the cylinder: the end-cap fans were built from arc points whose run
coordinate was a placeholder `0`, so the end discs were skewed out to `run = 0`
instead of sitting on the region's ends. It had been invisible because the
geometry test's box happened to start at x = 0, so the stray coordinate landed
inside the footprint. Two changes:

* the end fans now move each rim vertex out to the end it closes;
* the geometry matrix's test region moved away from the origin (x 30..42,
  y 20..40) precisely so that a leaked placeholder coordinate falls outside it.

This is the value of checking a rendered face against its region instead of
trusting a vertex count.

# Clean build and targeted memory check (PM item 6)

`scons -c` then a full rebuild from scratch (`evidence/clean_build.log`):

* GCC 16.2.0 (MSYS2 ucrt64), **0 errors, 0 warnings from the changed files**
  (the last two warnings in `slope.c` — an uninitialised read in a test helper and
  a truncating `snprintf` — are fixed);
* targeted memory check, 120 stress cycles: heap validation (`_heapchk`) after
  every cycle, **2,880 generated meshes, peak 3,312 vertices**, live mesh count
  back to baseline (`live +0 of 2907 made`), heap intact through the undo churn,
  cell count unchanged.

No new test campaign was started beyond this.
